# 初始化失败后的平台清理路径

2026-09-28，继续分析；无设备写入、模块替换或宿主操作。

从 `14000de94` 的失败出口追踪 `14000d990 -> 1400220e8 -> 140025a9c`。
与正常 StopAdapter 不同，这条路径销毁平台对象，随后把 device+0x418 清零。
失败出口接着调用 `140023714(device+0x418)`，但其空指针检查直接返回；不能把它当作
清理后又执行了一次固件恢复操作。汇编 `14000da13` 确认该指针确实被清零。

S3000 的 `14002d950` 仅在 platform+0x44 为 0（非 Guest）时安装 +0x9f8、+0xa00
等清理回调。已清零的 Guest 对象中，这些槽和 +0xa28、+0x1ad8 保持空值。
因此不能将 Native 的寄存器控制回调当作遗漏的 Guest 恢复步骤。

Guest 清理调用 `140025a48(platform, 0, 0)`，依次对槽 3、2、1、0 执行
`1400271d8`。已注册槽先清本地有效标记、调用槽清理回调，再向 BAR1+0x158 写
valid=0 的撤销描述符，随后释放本地页。槽 0 的回调只清空本地共享页指针。
然后解除共享区映射、释放设备信息和其他本地对象，最终解除 BAR 映射。
本次所执行的这段路径没有固件队列排空等待或 Guest OFF 写入。

`scripts/audit-failed-init-cleanup.py` 执行失败清理入口、平台销毁、Guest 回调安装、
四槽撤销及 BAR 解除映射的原始指令。16 种槽注册组合全部通过，记录撤销顺序及清空
结果；底层 MMIO、释放/解除映射以及五个其他子系统清理函数明确建模。
验证结果在 [failed-init-cleanup-oracle.json](failed-init-cleanup-oracle.json)。
它不覆盖被建模子系统的内部行为，也没有模拟 Host，不能证明释放旧固件资源安全。
撤销描述符的低 9 位得到验证；高位来自原函数栈值，不推断为新的协议字段。

该结果进一步排除了“销毁通信平台对象本身能确认固件停止”的假设。本机早先已执行
通信页撤销/重新注册并恢复 RPC，旧固件仍停在 Guest1/FW1、started=0、5/0。
本轮只读复核 RPC 回复 16,795 次、拒绝 0 次，固件状态不变。
