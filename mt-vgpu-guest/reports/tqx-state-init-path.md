# TQX 状态分配与初始化通知

本轮把状态资源追踪从 `ctxState` 取地址回调推进到 Windows 上下文分配和分页初始化。
**在已执行的普通分配路径中，初始化通知只记录 CPU 映射，不写状态模板。**
这缩小了先前“初始内容未知”的范围，但并不证明 OS 后备内容或 GPU 首次执行结果。
未做恢复、Host 操作或设备提交。

## 原始调用链

`00f008` 的普通分支请求 `01e000` 分配 `0x5000` 字节、`0x80` 对齐、映射参数
十进制10（`0x0a`）。它与 TQX 库的每核心 `0x180` 字节请求属于不同层次：
平台先取得完整上下文资源，库随后从该资源取地址和所需范围。

`00405c` 构造回调表，`00db50` 将它复制到 SIM 对象 `+0x1d0`，因此：

| SIM 偏移 | 回调 | 用途 |
| --- | --- | --- |
| `+0x260` | `006470` | 创建上下文资源 |
| `+0x268` | `006648` | 销毁上下文资源 |
| `+0x270` | `00700c` | 映射 GPU VA |

`01e000 → 01df28 → 006470` 构造 OS 分配请求，并由适配器 `+0x318` 回调分配。
完整 `0x58` 字节请求对照确认：大小 `0x5000`、对齐 `0x80`、上下文关联标志0、
allocation flags 9。随后 `00700c` 调用适配器 `+0x368` 映射 GPU VA；
测试中的映射请求为5页、普通堆范围、保护字段4。

Windows 为上下文资源提供独立的分页初始化操作，枚举值10；用途和数值由
[Microsoft 操作文档](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/ne-d3dkmddi-_dxgk_buildpagingbuffer_operation)
确认。资源分配及 CPU 映射通知的关系见
[Microsoft 上下文分配文档](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/nc-d3dkmddi-dxgkcb_createcontextallocation)。

参考驱动的实际分派为：

`1411c93d4(operation=10) → 0061c4 → 00a27c`

最终操作仅把资源描述符标志按位或2，并将通知中的 CPU VA 写到描述符 `+0x10`。
普通分配后的标志从 `0x0d` 变为 `0x0f`。没有写入 GPU 状态缓冲区。
操作10还会绕过适配器的一般分页抑制标志；空内部资源或空 CPU VA 返回
`0xc000000d`，描述符不变。再次通知会更新 CPU VA。

随后真实 `0219d0 → 041cc4(type=2)` 从同一描述符返回 GPU VA、CPU VA、
`0x5000` 大小，保留请求的128字节对齐，不改写状态内容。

## 可重复证据

运行 `python3 scripts/verify-tqx-state-init.py`，报告保存在
`reports/tqx-state-init-validation.json`。新增 oracle 为
`scripts/tqx_state_init_reference.py`，固定参考二进制 SHA256：
`0512ad5a75dcf16680d608e0a20b5154564798451d6b42224be9ae8e67d6ef33`。

- 8组完整分配、通知和取地址序列：4种预存字节模式及两种分页抑制标志。
- 完整OS分配请求和GPU映射请求逐字节对照。
- 3种OS分配失败：释放描述符和模型元数据，不映射GPU VA。
- 3种无效初始化通知：拒绝并保留原描述符。
- 1次CPU映射地址更新：只改描述符，不写状态内存。
- Unicorn 状态内存写指令监控为0，整块 `0x5000` 字节前后相同。

执行的是真实本地函数指令，但 Windows 分配/映射回调、池分配和
`1411c8214/1411c85dc` 元数据构造/销毁为明确模型。元数据关系依据
`011510 → 1411cb100` 静态结果设置；不声称执行了整套 Windows 内存管理器。
可选诊断后端设为不存在，未执行它的路径。初始化通知由测试模拟 OS 发起。

## 对 Guest 实现的影响

当前 Linux BO 创建时清零、命令上传保留状态内容的策略无需因这个入口而添加
额外的模板写入。这个结论只排除**上述已执行路径**中的模板，不能泛化为完整
硬件初始化证明，也不能把模型预填的零当作 Windows OS 的零初始化保证。

Linux 当前按 TQX 库所需范围保留一页；1～8核心的 `cores*0x180` 均能装入。
平台完整分配20KiB并不等于已证明 TQX 必须访问20KiB，也不构成一页实机足够的证明。
实际状态访问边界仍需 GPU 执行验证。

下一步无需继续在这个通知函数寻找状态模板；应推进完整上下文发布、已发布 VM
上的后续工作和安全退出。真正的首次执行、状态读写及复制结果仍未验证，硬件加速未启用。
