# TQX 单页复制命令的初始化与收尾

新增 `kernel/mt_tqx_stream.h`：在已验证的源/程序/目标 job 上，补齐初始 PDS、
结束控制字、296 字节软件状态记录及 16 字节命令页记录，形成 568 字节 CPU
镜像。限定新建命令对象、单个线性复制矩形、单页、无外部同步或已有状态。
**尚无 GPU 堆映射或实际提交；此镜像不能当作连续 GPU 缓冲区直接上传。**

## 从构造函数开始验证

`scripts/tqx_stream_reference.py` 执行真实 `1400d9b08 → 140119e88 →
14011964c → 1400a24f8`，由原始构造安装命令虚表 `140baef10`。命令分配器
自身的构造与 RAM/GPU 地址分配仍由模型提供，其参数经检查为 type5、20 DWORD
预留窗口。首次分配的页计数变化由真实 `14011a480` 处理并推导命令页 GPU VA。

执行构造暴露并修正了两个不能用全零对象替代的字段：

- `cmd+0x2278=1`：`14011d0f8` 将复制常量分配到 **type4**，不是零标志路径的
  type1。常量仍通过完整 GPU VA 被 PDS 装载，不能把它改成堆相对地址。
- `cmd+0x2220=1`：新建对象的记录序号是 1，最终记录 `+0xa0` 必须保存 1。

此前 `verify-tqx-programs.py` 在初始状态模型下验证了零标志/type1 分支的参数
编码；其字节结果有效，但不能作为真实新建对象的堆类型依据。本轮保留该独立
编码测试，并增加实际构造/type4 分支的整段对照。

设备虚表 `1403c4d40` 来自 `14004c518`，传输模块虚表 `140603ff8` 来自
`14009bb68`。已执行原始 getter：设备 `+0x158 → 14004cc38` 返回 0，
`+0x18 → 14004d0e4` 返回 `device+0x26a0`；模块 `+0x58/+0x68 →
140089a00` 返回 128。实际 `140091470` 将 feature `+0x246` 清零，避免猜测
这些会改变状态记录分支的值。其末尾查询 OS 配置的回调仍使用 RAM 数据。

## 初始 PDS 与结束记录

`140113c08` 内部的 `1401168e4(handler, cmd, 1, 0)` 选择 PDS 模板 1 和
shader 模板 1。前者代码偏移 0x20，后者偏移 0x40；`14011e634/14011b7f0`
生成 16 字节 PDS 状态：`[0x90000247, 0, shader_heap_base+0x40, 0]`。
该状态独立于 job 内的执行 PDS 和常量装载 PDS。

发射顺序中的五段分配如下；表中对齐是字节，参考参数以 DWORD 表示：

| 用途 | 字节数 | 对齐 | type |
| --- | --- | --- | --- |
| 初始 PDS 状态 | 16 | 16 | 4 |
| job 执行 PDS 状态 | 36 | 16 | 4 |
| 源描述符 | 64 | 32 | 5 |
| shader 常量 | 20 | 4 | 4 |
| 常量装载 PDS 状态 | 16 | 16 | 4 |

`1400dad24 → 14011b3cc` 保存当前 job 状态和尾部位置。随后执行真正的
`14011d194`：

1. `14011e768 → 1400dad64` 将命令尾部控制字从 0x25 改成 **0x2d**。
2. `14011df28` 保存 296 字节软件状态记录。
3. `14011d378/14011de48` 保存 `[command_va, 80]` 的 16 字节页记录。
4. `14011d488/1400db2c8` 把页长度按 32 字节上取整后写回记录 `+0x30`。
5. `140119914` 的分配器所有权/结束处理仍为模型，不宣称已验证资源发布。

最终软件记录的非零字段：

| 偏移 | 值 |
| --- | --- |
| 0x18，64 位 | 命令页 GPU VA |
| 0x30，32 位 | 96，来自 ceil(80/32)×32 |
| 0x34，32 位 | PDS 代码堆相对基址 +0x20 |
| 0x38，32 位 | 初始 PDS 状态堆相对地址 |
| 0x3c，32 位 | 0x08040001 |
| 0xa0，64 位 | 新建对象序号 1 |
| 0x124，32 位 | 原始 job 字节数 80 |

这里的软件记录、命令页记录与固件队列包是不同层。单页 GPU VA 必须非零、
4096 对齐且在 40 位范围，PDS 状态为 16 字节对齐；组合构造继承 job 的源/目标
跨度、常量和代码范围检查，任何阶段失败均不改写输出。

## 验证及遗漏函数补全

- `verify-tqx-stream.py`：190 组五种元素大小、尺寸端点及随机地址，从真实
  命令对象构造到 job 和最终收尾，逐段比对所有 GPU 数据、记录；15 个拒绝案例。
- `tqx_program_test.c`：ASan/UBSan，尾部保护、晚期失败原子性、页和状态上界。
- W=1 主模块构建与 `mt_guest` ABI 对照通过；新 stream 为内部 CPU 编码组件，
  未增加 GPU 提交入口。
- 69 项真实内核 GEM/RAM 检查通过，临时模块已卸载；主模块未加载，只有 QXL
  card0，未执行恢复、Host 操作或 GPU 工作。

此前未识别的叶函数 `1400da520` 已通过现有 Ghidra 工程补定义、反编译和保存，
导出到 `decompiled/mtkm64.sys/recovered-tqx/`，`corpus.py function` 可直接查询，
并已纳入原始指令对照。另补存 `14011d758`（虚表 +0x38，读取 3 个状态 DWORD）
和 `14004c138`（+0x3c0，空实现）；这两个叶函数本轮仅静态分析，未声称执行验证。
后续还应继续补齐间接调用目标，不能把批量分析成功当作
所有函数边界均已正确识别。

## 后续适配

多拆块组合、状态复用和根导出随后已由 [完整单区域编码](tqx-copy-stream-path.md) 补齐。
下述当时的多 job/导出缺口已被该验证替代，堆映射和真实提交仍未完成。

单 job 的初始和收尾编码已有依据；仍需把最多四个拆块串起来、处理状态复用，
实现 type4/type5 和 shader/PDS 专用堆的真实 VM 映射/分配，再接软件记录导出与
固件提交。命令对象 `+0x30 → 14011d6bc` 导出的是记录数量和命令根 VA 列表，
不能沿用 CE 的 48 字节导出结构；本轮只静态追到这个入口，尚未执行转换。

复现：

```sh
python3 scripts/verify-tqx-stream.py
python3 scripts/verify-runtime-integration.py
python3 scripts/verify-gem-kernel.py --kind gem --run
python3 scripts/corpus.py function mtkm64.sys 1400da520
```
