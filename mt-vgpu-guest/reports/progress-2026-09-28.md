## 最新继续适配：对照 Native core 的 PVZ Host 映射半边

从官方 2.3.0 core 确认 Guest 的固件 heap map 请求为 `funcID=1, devID=0, size=8 MiB,
PAddr=PhysHeapGetDevPAddr`；unmap 为 `funcID=2, devID=0`。再对照 Native 2.7.1
core，确认它的 server 半边按 OSID/在线状态调用 `RGXFwRawHeapAllocMap` 和
`RGXFwRawHeapUnmapFree`，但该 core 的 Guest client 槽仍是 NOT_IMPLEMENTED stub；
它的分配器要求 256 MiB、OSID=0，是单 OS Native 构建；官方 2.3.0 分配器则要求
8 MiB、OSID<15，与目标 Guest 的调用相符，但该候选的 server 入口仍返回
`INVALID_PVZ_CONFIG`。因此不能交叉复用 Native core 作为 Guest provider/Host 服务。
本地材料没有找到匹配的 Guest 到 Host PVZ transport；Hyper-V CPUID 能力位也无法
提供缺失的 MTT Host 接口。没有把 Guest stub 改成假成功或试发未知 hypercall。反汇编与结论见
`reports/pvz-map-abi-and-host-half.md`。全为离线分析，未操作设备或宿主。

## 最新反编译追踪：普通 TQX 节点不调用二级根回调

继续追 `CreateContext` 后确认：普通有效硬件节点创建 SIM context；`SetRootPageTable` 会更新
Guest Context+`0x30`、Process+`0xa8` 及一个设备侧 root 槽。`140003498` 的 `+0x250` 间接回调
仅在替代上下文对象非空时触发，普通节点的该槽为空。TQX 工作包本身携带 root，因此 Linux固定根任务不需要臆造一个
PCI/RPC 根发布步骤。扩容后的根替换和页表/TLB 撤销仍未验证，封存 VM 最终销毁门保持关闭。

任务包携带该根。完成第一个模拟任务后，第二次准备复用同一根，页表 BO 没有再次写入/读回且内容不变。
`W=1` 主模块和自测模块构建通过；fence 自测 **330 项**、GEM 自测 **280 项**通过，两个临时自测模块
