# CE3 复制命令段：初始化、同步和收尾

后续已还原一条记录导出/分页转换路径，见 [最新转换实现](ce-paging-path.md)。
以下保留本阶段的证据与当时尚未追通的线索。

本轮继续 Guest 端源代码适配，没有处理恢复、操作宿主或向 GPU 发布任务。

## 新增原始指令证据

上轮只有 40 字节复制载荷。本轮连接执行：

- `1400e4d04`：CE3 段初始化与跳转，预留 6 DWORD 状态加 8 DWORD 控制区，共 56 字节。
- `1400e5df4`：40 字节线性复制。
- `1400e4b7c` → `1400e5360`：待完成复制的同步指令，24 字节；没有目标地址写入。
- `1400e9420`：16 字节结束指令，32 字节对齐的附加状态数据和 256 字节库内描述记录。
- `1400e9b88`：回填段长度，此序列为复制 40 + 同步 24 + 结束 16 = 80 字节。

原始 allocator 以 0x26 DWORD 窗口预留，再由 commit 退回未使用部分；单纯把提交
指针视作“分配一个完整页”会误读 `1400fcac0` 和初始根地址。本轮 RAM 模型明确保留
预留/提交行为，采用 4 KiB 分块，原始初始化真正跨到新块后才取得该命令段根地址。
没有执行原始 OS 分配器或硬件映射。

## 已验证的限定布局

`kernel/mt_ce_stream.h` 新增 `mt_ce3_stream_prepare`，生成 176 字节命令段与
256 字节软件库记录。适用前提是 CE3、单条复制、显式同步、无可选前缀、无外部
同步和保存状态；目前不自动判定本机满足这些前提。

| 命令段偏移 | 内容 |
| --- | --- |
| 0x00 | `0x4000000000000000 \| (command_va + 56)` |
| 0x08 | 回填的 80 字节段长度 |
| 0x10 | `0x5000000000000001` |
| 0x18..0x37 | 预留状态，清零 |
| 0x38..0x5f | 已验证的 40 字节复制载荷 |
| 0x60..0x77 | 同步指令 `0x1000000010000008`，其余清零 |
| 0x78..0x87 | 结束指令 `0x5000000000000000`，其余清零 |
| 0x88..0x9f | 对齐填充，清零 |
| 0xa0..0xaf | 附加状态 `[24, 0]` |

软件记录仅非零字段为 +0=32、+8=command_va+160、+16=command_va、+40=24。
**这份 256 字节记录不是 80 字节固件提交包，也尚不能直接当成 DMA 提交载荷。**

## VM/GEM 接入与边界

新增内部 `prepare_copy_stream` 取得同一文件的命令、源、目标三个 GEM 引用，验证
设备/管理器和实际 VM 绑定。命令区要求 32 字节对齐，176 字节不跨 4 KiB 页；
源/目标沿用 40 位范围和重叠检查。命令区也不能与任一数据区共享重叠后备地址。
三者可以是同一 BO 的互不重叠部分，每次 lookup 的引用都独立归还。

输出仍是 CPU 暂存对象，没有写命令 BO、上传 VM、创建 GPU 使用引用或开放提交。
错误输出、版本、对齐、空间、句柄或重叠条件都会拒绝，失败保留原输出。

## 验证

`scripts/verify-ce-stream.py` 对 **128 组**不同 40 位地址、页内位置、复制长度和
字段控制执行原始初始化/复制/同步/收尾。全部 176+256 字节与新实现一致，输出尾部
保护保持完好。模型明确关闭可选前缀、外部同步和保存状态，显式模拟分配/提交、
平台 predicate、记录存储及对象重置；这不是实际 GPU 执行。

GEM ASan/UBSan 测试覆盖三重相同句柄、逐次 lookup 失败、跨文件/管理器、源/目标
覆盖命令区、跨页/对齐、容量和版本拒绝，引用平衡。全部集成测试通过，主模块 W=1
编译无警告且 `mt_guest` ABI 不变。真实内核 GEM/RAM 测试增至 **29 项**，
分配/释放平衡，临时模块卸载；主模块未加载，没有 MTT DRM 节点。
