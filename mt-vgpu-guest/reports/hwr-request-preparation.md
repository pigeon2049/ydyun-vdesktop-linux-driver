## 已准备的操作

`kernel/recovery/mt_hwr_request.c` 仅用于已调查的保留会话：

- `enable=1` 加载时只建立 sysfs 属性，不触发硬件恢复。
- 每次回调持有设备锁，重新验证绑定模块；读写会话时持有 trial mutex。
- 主模块引用保留到辅助模块卸载，避免主模块卸载导致页面被释放。
- 控制入口仅 root 可写，只有准确命令 `request-hwr` 才可能执行。
- 执行前检查 PCI 身份、通信注册、协商结果、OSID=4、既有固件地址与长度、
  Guest1/FW1；新试验或本轮已发布资源均拒绝。
- 每次加载最多尝试一次，在写入前记录 attempted，随后只写 64 位 BAR1+0x118=1。
  不追加固件命令，不清零共享控制字段，不修改 Guest 状态，不自动重试。
- 返回写入成功仅表示调用执行，**不表示 Host 接受或 GPU 恢复成功**。

这里复现的是参考 Guest `140022f24` 的通知动作，不是完整 Windows TDR 生命周期。
初次连接尚未完成，所以也没有伪造运行上下文或调用原生 GPU 寄存器复位。

## 为什么需要扩大作用范围的明确授权

静态证据来自旧 Host 2.3，不是当前 Host 二进制：

1. BAR1+0x118/value=1 经 `vgpu_hwr_request` 调度 `vgpu_mpc_hwr_work`。
2. `vgpu_mpc_hwr_work` 异常分支调用 `reset_gpu`（0x117d50）。
3. `reset_gpu` 根据 MPC 核心配置生成复位掩码，调用
   `mtgpu_smc_reset_subsystem`（0x117e18 或 0x117e63）。
4. 成功后调用 `LoadWindowsFirmwareRobust`（0x117e2f）。

因此这条 Guest 入口能请求宿主硬件子系统重置及固件重载，影响范围不能确认只限本 VM。
用户此前授权的是本机适配，且无法操作宿主；尚未明确授权影响同 GPU 的其他虚拟机。
已发出一次授权询问，未收到明确答复前不发送请求，也不重复询问。

若获得授权，先重新核对现场和模块散列，保存恢复前快照，加载辅助模块后仅请求一次，
随后通过现有只读接口观察固件、队列、共享页、IRQ/RPC 与桌面服务并保存日志。
根据实际响应决定后续步骤；不把超时当作授权重复、不强改 Guest=0，也不据此释放旧映射。

当前只加载主通信模块，辅助模块已卸载。没有安装任何自动加载或自动恢复配置。

注意：主模块初始化共享页时把健康首字节设为 1；后续 Host 也可更新它。只读值 1
仅说明 Guest 当前看到该值，不是独立硬件健康检测，更不能当作重置必然无影响的证明。
