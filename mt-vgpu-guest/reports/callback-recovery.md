## 已确认的函数边界错误

共享通道回调表 `0x141106500` 的槽 0/1/2/3 都引用 `0x140024ee4` 作为描述符构造函数。
旧分析却将它并入 `140024e48`：该函数末尾 `140024ee2` 的 `int 0x29` 是快速失败终止，
不是落入下一函数继续执行。旧伪 C 因此在损坏链表分支中出现了不相关的注册描述符算法。

本轮对这个经过汇编/回调表双重核对的边界做了定点修正：将快速失败路径设为终止流，
从旧函数体分离 `140024ee4..140024f12`。修正前后原二进制均未变化。
Ghidra 对快速失败和间接调用的伪 C 仍可能有类型及返回形式误差，实际语义以指令为准。

## 对 Guest 适配的直接结论

| 入口 | 还原动作 | 与本机实现的关系 |
| --- | --- | --- |
| `140024ee4` | 构造共享页槽号和 4096 字节大小；调用者随后置 valid 位 | 当前注册值正确，4 个槽的原始指令对照通过 |
| `140024f14` | 保存页 0 CPU 指针，仅把页首字节置 1 | 解释了健康值 1 的 Guest 初始化来源；没有额外 Host 通知 |
| `140024f24` | 清空本地页 0 指针 | 不是固件重置或解绑通知 |
| `140027284` | 根据槽号取共享页 CPU 地址 | 当前四页索引一致，4 个槽对照通过 |
| `140027350` | 将消息环编号写 BAR1+0x138 | 当前 RPC doorbell 已实现；4 个环对照通过 |
| `140027274` | 输出值清零并返回 -4 | 该回调没有可移植的恢复操作 |
| `140027370` | 唤醒 Windows 事件等待者 | Linux 已使用 IRQ/work 处理；不等于缺少设备启动寄存器 |

新增共享页 `+0x328` 操作回调涉及按通道读/清标志，尚未当作固件启动动作移植。
仅看到可写字段不足以证明应当在当前停滞现场写入。后续可利用补齐的入口继续追踪
中断分发和 Guest 内恢复握手，而不依赖宿主操作。

这次补充缩小了原调用图的遗漏范围，但未找到能直接解除现有固件停滞的新写入步骤。
没有把反编译进展等同于 GPU 可用；硬件连接、DRM render 和用户态加速仍未实现。
