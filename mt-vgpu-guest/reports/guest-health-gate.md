本轮全部操作在 Guest 内完成。仍未实现硬件加速；当前会话保持原来的通信恢复模块，

## 已修正的代码遗漏

`1400168b4` 的可选平台回调启用时，原始代码读取 `140023874` 返回的共享页 0
首字节。若该值为 0，先等固件状态变成 READY(1)，最多 400 次、每次 25 ms；
每次未 READY 时重发 online 通知。超时前不写 Guest=1，不排入连接命令。
`140016b4c` 在同样健康值为 0 时直接失败，不发送断开命令，不写 Guest=0。

此前 `mt_fw_connection.h` 只实现了健康值非零的路径。本轮增加必需的 `gpu_normal`
回调，在 `mt_guest_probe.c` 从已注册的共享页读取该值。未注册完整通信页时按异常处理。
断开异常返回 `-EHOSTDOWN`；该错误和其他失败一样，不授权释放已发布资源。

`verify-fw-connection.py` 现在执行参考驱动的真实首字节读取，并比较包括健康检查在内
的调用顺序。36 个状态机案例全部一致，覆盖 READY 在 0/1/399/400/401 次观察边界、
异常健康值、非零 255、超时和拒绝连接；另外 2 个入队失败传播案例通过。
内核 `make -C kernel W=1` 无警告通过，现有 18 个单元测试通过。

新模块只编译，未替换在用模块：当前 `recover_channels=1` 模式根本不执行连接/断开，
重新加载不会验证本次修改能否启动固件，且会重置会话内一次性通知标志。
在用模块已另存 `build/recovery-channel/loaded-6f2599bec31bc199bd0dcce1bbb0caa61a022aecbe8aa92294ee3e7b87d1553b.ko`。
新旧散列、测试范围见 `guest-health-gate-validation.json`。完整新启动仍未实测。

## 内核恢复入口与作用范围

先前 MTML reset 叶函数不支持操作的结论，仅限 MTML 路径。内核还有另一条路径：

`140017110 -> 1400088c0 -> 140022f24 -> BAR1+0x118 = 1`。

`audit-guest-recovery.py` 对原始 `1400088c0` 执行 8 个纯内存案例，验证通知值，
以及本地标志为 1、状态为 2 时清零共享 +0x10/+0x18 的条件；没有设备访问。
同时保存了反编译库中 20 处直接调用 BAR1 64 位包装器的清单。清单不覆盖间接调用
或其他 MMIO 原语，不能称为完整协议规范。

旧 Host 2.3 对 +0x118/value=1 的处理调用 `vgpu_hwr_request`（0x53f90）。
其异常分支调度 `vgpu_mpc_hwr_work`（0x4a3a0），工作函数仍判断异常时调用 `reset_gpu`。
因此它是向 Host 请求 GPU/MPC 级恢复，不能当成本虚拟机专用的软件复位。
当前 Host 二进制和作用范围未核实，本轮没有触发该请求。证据见 `guest-recovery-audit.json`。

## 实机只读结果

`build/recovery-channel/capture-49df4846d743/report.json` 保存 10 秒状态观察：

- Guest=1、FW=1、started=0，DM0 队列仍为 head=5/tail=0。
- RPC 已回复 1135 次，拒绝 0；没有 IRQ10 nobody-cared 错误。
- 共享页健康字节为 1，控制 +0x10/+0x18 原始值均为 0。
- SDDM、SPICE、Tailscale 均 active，只有 QXL card0，没有 MTT render 节点。

健康值非零说明本次补齐的异常门控不会改变这份现场的连接路径，不能把修正宣称为
现有故障的解决方案。共享 +0x10/+0x18 的用途与旧 Host 头文件已不同，因此诊断工具
保留原始字段名称；它们为零也不能证明 Host 没有其他恢复状态。

当前实际障碍仍是已发布的固件未运行、既有命令没有被消费。Guest 通信正常和 CPU
指令对照通过，都不能代替固件连接、DRM 和用户态图形加速的实际验收。
