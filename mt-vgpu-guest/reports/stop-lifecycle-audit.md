# StopAdapter 不是已确认的保留会话恢复接口

2026-09-28。本轮仅执行本地反编译查询及 Unicorn 原始指令验证，未写设备。

## Windows 停止路径

继续追踪上下文生命周期时，发现 `1411c658c -> 14000e18c` 的 StopAdapter 路径：

1. 外层先停止工作线程、回调和定时器，并调用其他子模块停止回调。
2. `14000e18c -> 14001759c -> 140017680` 遍历已分配固件上下文。
3. Guest 分支调用 `140016b4c` 请求断开，但 `140017680` 不检查其返回值，继续资源清理。
4. `14000e297` 明确设置 R8D=0，随后调用 `140023afc(gpu, 3, 0)`：这里的 3 是
   “写 Guest 状态”操作编号，**实际写入 BAR0+0x890 的值是 0，不是 Guest3**。
5. `140023998 -> 1400262d4` 在 info flags bit0 开启时写 BAR1+0x78=1。

Ghidra 伪 C 省略了第 4 步的第三个实参；原始汇编和指令执行确认了真实值。
初始化失败的 `14000de94` 则走 `14000d990`，不能将 StopAdapter 等同于已失败启动的
完整恢复流程。它们的线程状态、已发布上下文和资源所有权前提不同。

## 原始指令验证

新增 `scripts/audit-stop-lifecycle.py`，执行完整 `14000e18c` 正常控制流以及
`14001759c / 140017680 / 1400155a4 / 140023afc / 140023998 / 1400262d4`。
锁、断开结果、外部清理及底层 I/O 被明确建模/记录；不访问硬件。

8 个案例覆盖有无 layout/已分配上下文、断开返回失败或成功、info bit0 开关。
断开失败的案例仍观察到资源清理、Guest OFF 写入，以及条件成立时的 +0x78 通知。
因此 **StopAdapter 返回 0 或 Guest 状态回读 0 都不能作为固件已排空队列的证据**。
输出为 `stop-lifecycle-oracle.json`。本测试不模拟固件，不证明资源释放在当前会话中安全。

## 旧 Host 2.3 对照与边界

- `vgpu_access_pci_bar0_region` 的 `4d237..4d24c` 将 +0x890 写入对应 OSID 的状态槽，
  该分支本身不等待队列排空或确认释放。
- BAR1 内建 `+0x78` 分支 `54c0f..54c25` 调用
  `mtgpu_mdev_notify_vpu_driver_unload.part.0`，后者遍历已注册 VPU 回调。
  不能仅凭它名为“卸载通知”就视为 GPU 固件断开确认；BAR1 还存在前置注册回调链。
- 单独的 `mtgpu_vgpu_vm_offline` 会修改在线位并发送 opcode=0x6e 的 Host 固件命令，
  但没有从上述 Guest StopAdapter 通知直接到达它的证据，不能把 Host 内部函数
  当作可从 Guest 直接调用的接口。
- 这些都是本地旧 Host 对象的静态证据，不是当前 Host 的执行观测。

## 本机决定

当前是跨 Guest 重启保留的 Guest1/FW1、started=0、DM0 5/0 会话，没有连接后上下文，
现有模块仅恢复通信。尚无能确认固件停止引用旧资源的 Guest 端信号。
本轮不强写 Guest0、不释放或覆盖旧固件、不发送 +0x78，也不触发 HWR/MPC 重置。
保留通信服务，并将这一路径与实际初始化失败路径区分，避免用状态值变化冒充恢复。
