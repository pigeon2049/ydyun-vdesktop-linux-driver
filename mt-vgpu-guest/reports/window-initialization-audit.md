# 平台窗口初值与资源枚举核查

2026-09-28。继 `mt_guest_windows_refresh` 后，新增 `mt_guest_windows_build`，
将已确认的零初值、BAR2 描述和窗口刷新连接起来。仍是 CPU 侧构造，未发布到设备。

## 初值来源

`1400222b4` 分配 0x3e48 字节，随后显式清零整个对象，再进入平台初始化。
原始指令验证故意让模拟分配器返回全部 0xa5 的缓冲区，确认不是依赖模拟器的零内存。
布尔分配参数只由 DL 传递，验证按低 8 位检查，未将寄存器高位误当成参数。

`14002fe44` 读取 PCI BAR 与 Windows 翻译后的资源列表，在 platform+0x400 写入
BAR2 GPA、BAR2 长度、0；`140026390` 再刷新其余已知字段。资源列表里普通 memory BAR
和大于 4 GiB 的 large-memory BAR 使用不同长度编码，本次均执行原始资源解码指令。
后续 `1411ce6b8 -> 14002c944` 的 Guest 分支只构造独立的 WDDM 分段输出；验证执行后
该 280 字节区域保持不变。Native 分支中的额外窗口写入不适用于本设备。

## 新代码及验证

`mt_guest_windows_build` 检查 BAR2 对齐、长度、地址溢出及设备实际大小，先在临时
缓冲区构造完整已恢复区域，再提交到输出；失败时不污染输出。不解析 Windows 资源
列表作为 Linux 运行输入，Linux 调用者应传入 PCI 核心已枚举的资源值。

`verify-window-initialization.py` 验证：

- 原始构造器清零完整 15,944 字节对象。
- 3 个 BAR2 GPA × 2 个 BAR2 大小，共 6 个资源枚举、窗口刷新和后续分段构造案例。
- 每例比较全部 280 字节及尾部哨兵。
- 6 个畸形 BAR2 输入拒绝并保持输出不变。

结果 `window-initialization-validation.json`。此前 65 个刷新对照及 15 个异常输入
案例也重新通过。C 包装器使用 UBSan、Wall/Wextra/Werror。

## 仍需集成

本次执行了构造器清零、资源枚举、刷新与后续分段构造；构造器中的完整初始化回调
绑定仍被模型替代，不能称为整个 Windows 初始化过程的仿真。四个系统/平台输入
仍由调用者明确提供。280 字节跨度不是已证明的 Host 拷贝长度。
持久缓冲区、上下文发布以及 Host 引用撤销确认尚未实现；本轮没有加载新模块或写设备。
停止生命周期的进一步调查见 [StopAdapter 核查](stop-lifecycle-audit.md)。
