# 共享页 +0x328：显示中断标志，非已确认的启动握手

2026-09-28。仅离线原始指令执行和 sysfs 只读核查；未操作宿主或写设备。

## 回调身份与行为

`mtkm64.sys:140003eb0` 构造的回调表包含：

| 表内偏移 | 包装入口 | 实际叶入口 | 共享页 0 的动作 |
| --- | --- | --- | --- |
| +0xf8 | 1400066f8 | 140022430 | 设置 DWORD +0x328 的 bit(channel*8) |
| +0x100 | 1400066e4 | 140022280 | 清除同一使能位 |
| +0x108 | 14000645c | 140021ee0 | 测试 bit(channel*8+1)，为 1 时清除并返回 AL=1，否则 AL=0 |

三个包装入口经 adapter+0x248、device+0x418 找到 GPU 对象；GPU+0x1cd0 是共享页 0
CPU 指针。GPU 或共享页为空时不写内存。叶函数只有内存位操作，没有 MMIO doorbell，
也没有固件启动、队列排空或资源释放等待。布尔返回仅定义 AL，不能解读高位。

`mtdispkm64.sys:140005360` 将这份 0x110 字节表复制到显示对象 +0x18，所以相应槽
变为 +0x110、+0x118、+0x120。`1400017ac` 的 Guest 分支根据 enable 参数选择前两者，
汇编确认通道参数仍经 EDX 传递（伪 C 省略了这个实参）。它由 `140006108` 按显示
通道掩码调用。显示中断处理 `140006420` 调用第三个回调测试/确认待处理标志。
这些上下文支持“显示中断开关与确认”的解释，不能把它命名为固件启动请求。

## 启动顺序约束

主驱动 `1411c62b8` 先执行 `14000de94`；只有成功，才构造上述表并调用显示模块。
`14000de94 -> 1400174fc -> 140016dcc -> 140016218` 包含固件加载和连接；失败返回后
不会执行该显示初始化步骤。这与把 +0x328 写入提前当作连接前置条件不相符。
这里的顺序依据来自现有伪 C 与汇编人工核对，不是完整跨模块初始化仿真。

## 验证与实机限制

新增 `scripts/audit-display-shared-flags.py`：执行表构造及三个包装/叶函数的原始指令，
4 个通道、5 组混合标志、3 个操作共 60 个案例，通过整页比较确认未修改其他字节；
另有 6 个 GPU/页空指针保护案例。没有执行 Windows OS 或任何硬件 I/O。
x86 位索引会回绕，但这不能证明通道号超出 0..3 是合法协议输入。

`--live` 从已加载模块的 `channels_raw` 读取四页快照：本机 page0+0x328=0，固件仍
Guest1/FW1、started=0、DM0 5/0，RPC 继续服务。这里的 0 只是瞬时读数，不证明该
字段从未变化。结果见 [display-shared-flags-oracle.json](display-shared-flags-oracle.json)。

本轮消除了此前共享页标志回调的语义疑点，没有找到可用于当前固件停滞的新启动操作，
没有向运行模块添加尚无调用前提的显示中断开关。硬件加速仍未完成。
