# TQX 目标发射与组合 job 镜像

已实现本机 family2 的 80 字节目标命令编码 `kernel/mt_tqx_destination.h`，
并用 `kernel/mt_tqx_job.h` 组合源描述符、程序状态和目标命令。输出为 240 字节
CPU 镜像：64 字节源分配内容、96 字节程序状态及元数据、80 字节目标命令。
它不是连续上传即可执行的 GPU 命令流：三个部分属于不同分配，专用堆映射、
初始命令状态、同步和最终封装仍未接入。没有 GPU 执行或恢复操作。

## 原始路径和字段

固定参考 `/opt/MTT-driver-only/mtkm64.sys`，SHA-256 为
`0512ad5a75dcf16680d608e0a20b5154564798451d6b42224be9ae8e67d6ef33`。
复制 job `140113c08 → 14011e4c4` 经虚表 `+0x560` 调用 `1400dc638`。
该函数先清零 80 字节，调用 `1400d9eec/14011eb2c` 编码几何和目标格式，
填入三个 PDS 相对地址及常量数量，最后调用 `1400da4a8`、`1400d98c8` 发射。

| 字节偏移 | 已验证的单层线性复制字段 |
| --- | --- |
| 0 | 0x40000005；16 字节元素为 0x42000005 |
| 4 | 1/2/4 字节元素为 0x2da100，8 为 0x2d2100，16 为 0x1a2100 |
| 12、16、24 | H−1、W−1、W−1 |
| 28、32 | 目标 GPU VA 低 32 位；格式字段与高 8 位 |
| 36、40 | 2、0xa8000000 |
| 44、48 | W−1、H−1 |
| 52、56、64 | PDS 常量装载代码、执行状态、常量装载状态的堆相对地址 |
| 68、72 | 0x08000001、0x25 |
| 其余 | 0 |

格式字段依次为 `0x140000/0x150000/0x168000/0x118000/0x48000`。
地址不是 BO 物理地址，三个 PDS 字段也不是完整 GPU VA。Linux 检查 16 字节
PDS 地址对齐、状态范围、40 位目标跨度及 1–32768 的矩形尺寸；保留参考支持的
未对齐源/目标数据地址。无效输入包括后期失败均保留原输出。

`1400d98c8` 从命令分配器 `cmd+0xb58` 取得位置，拷贝 80 字节并提交新指针，
`cmd+0x2190` 增加 80；`1400dbf64` 将末尾控制字位置写入 `cmd+0x2298`，
`cmd+0x22b0/0x22b1` 置 1。这些参考副作用也在验证中检查。

## 验证结果

- `verify-tqx-destination.py`：490 组五种格式、宽高边界、40 位地址端点、
  全部地址低四位及随机 PDS 地址，80 字节逐字节一致；17 个拒绝案例通过。
- `verify-tqx-programs.py`：192 组组合 job 执行原始源编码、参数重排、PDS
  补丁及真实 `14011e4c4` 虚调用、目标发射，源/程序/目标逐段对照通过。
  源分配最后 16 字节是 Linux 清零策略，参考只写前 48 字节。
- `tqx_program_test.c`：ASan/UBSan，输出尾部保护，早期及后期错误的原子性，
  对齐/范围端点检查通过。
- `verify-runtime-integration.py`：既有生命周期测试、W=1 主模块构建和
  `mt_guest` ABI 对照通过。组合 job 目前是独立内部编码组件，未增加用户接口。
- `verify-gem-kernel.py --kind gem --run`：63 项真实内核 RAM 检查通过，
  临时模块已卸载。PCI 设备未绑定，前后只有 QXL card0；主实验模块未加载。

地址分配、命令缓冲区预留/提交、初始状态和最终完成回调仍由 RAM 模型提供，
此验证不能证明这些部分可用于显卡执行。没有将新编码组件作为已验证的 GEM
专用堆分配入口暴露。

## 后续已补齐的收尾路径

以下缺口随后在限定单页、单 job 条件下补齐，见 [单页初始化与收尾](tqx-stream-path.md)。
真实对象构造还纠正了初始序号和常量的分配类型。

原始 job 在目标发射后调用虚表 `+0x510 → 1400dad24 → 14011b3cc`。
`14011b3cc` 还处理 0x128 字节状态缓存、计数以及必要的状态记录发射，之后
`1400dad24` 将 `cmd+0x2298` 移到 `cmd+0x2290` 并清零前者。
所以当前 80 字节结果不能省略收尾而直接提交。

静态表 `140baef10` 的后续入口已保存到 `tqx-command-vtable.json`：
初始化 `+0x528 → 14011a480`、`+0x520 → 14011a62c`；
程序初态 `1401168e4 → 14011e618/14011e634`；
状态记录 `+0x478 → 14011e768`。需沿真实分配和状态记录继续，还不能把这些
未验证的回调替换成空操作后声称完成命令流。

发现 `+0x490 → 1400da520` 未被既有 Ghidra 函数索引识别，但完整汇编保留了
该 80 字节叶函数：清除 `cmd+0xb88` bit0，并清零 `+0xb80/+0xb7c/+0xb78`。
这说明批量反编译库仍可能遗漏间接调用目标；后续应补充函数识别和导出。
后续已保存 Ghidra 补充反编译，并纳入单页原始指令对照。

复现：

```sh
python3 scripts/verify-tqx-destination.py
python3 scripts/verify-tqx-programs.py
python3 scripts/verify-runtime-integration.py
python3 scripts/verify-gem-kernel.py --kind gem --run
```
