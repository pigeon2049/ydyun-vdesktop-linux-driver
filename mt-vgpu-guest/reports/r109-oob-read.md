# r109：P+0x54 是堆越界读（usable 56），邻居决定成败

r108 的下步执行完毕，结论出人意料却证据确凿：
`malloc_usable_size(P) = 56`，而读到 `+0x50/+0x54/+0x58`——
**厂商代码自己在堆越界读**（`Calloc(0x30)` 的对象读到 +0x58）。
`+0x54` 的值 = 邻居堆块内容：我方最小流程里恰为 0，
真应用（分配繁忙、surface/堆林立）大概率非零即过。
离线 gdb，零硬件触碰。

## 证据

- `P=0x55555556a030`（CCB 入口读 create+8，跨 run 模板稳定），
  `malloc_usable_size → 56`。
- 写入者唯一（watchpoint）：`RGXCreateDeviceMemContext` 内
  `*param = __ptr`（`Calloc(0x30)` 对象），别无他人。
- 故 `+0x54`（偏移 84）超出 56 可用区 28 字节——读邻居。

## 含义（方向级）

1. 追"+0x54 写入者"是伪命题：**没有写入者，只有邻居**。
   r95–r108 十四轮追的"计数槽"并不存在——它是悬空偏移。
2. Rogue2D 整形的正确打法从"填槽"变为**堆布局喷洒**：
   在 CCB 之前制造分配，让 P 邻居落非零（surface/堆/PMR 描述均可），
   看 size 是否转正。这比精确整形廉价一个量级，且与厂商真实行为一致
   （真应用靠繁忙堆"蒙混过关"，这是 vendor 代码的原罪，不是我们的）。
3. 同家族解释 r72 的 render-create 偶发崩溃（堆垃圾敏感）——
   同一类 OOB/未初始化 reads，离线 flake 的总根。
4. 对翻译器的直接价值：UMD 侧这类 OOB 意味着**不能逐字节信任
   UMD 堆对象的"语义"**——T1 拷贝必须严格按 counts 定界
   （r62 的钳制设计再确认），多一字节都可能是邻居。
