# Guest 内存窗口刷新函数还原

2026-09-28。本轮继续补齐 Linux Guest 所需的数据构造，未写设备，固件仍未启动。

后续已追加 `mt_guest_windows_build`，验证零初值和 BAR2 资源枚举，见
[窗口初始化核查](window-initialization-audit.md)。下面保留最初仅刷新阶段的范围说明。

## 缺口与调用顺序

此前 `mt_fw_context.h` 已能构造 80 字节的连接后上下文，但其中 `+0x40` 指向的
平台内存窗口缓冲区尚无 C 实现。此字段应是该缓冲区的 Guest 物理地址，不能直接
填写 BAR2 基地址。Windows `1400231ec` 取 outer GPU+0x408 的物理地址，即
inner platform+0x400 所在的内存，随后写 BAR1+0xf0。

`140026064` 在取得设备信息后调用 `140026390`，刷新平台内存窗口中的分区字段。
`140016dcc` 仅在 `140016218` 返回连接成功后调用 `14001ecdc -> 1400231ec`。
因此该缓冲区是完整驱动的必要准备工作，**不能通过提前发布它来绕过当前连接失败**。

## 新增实现

`kernel/mt_guest_windows.h` 的 `mt_guest_windows_refresh` 对应 `140026390`，
输入包括设备信息和四个原始平台/系统字段，修改平台 +0x400..+0x517 的已知部分：

- 根据首个 flags&3 分段构造普通内存及私有区范围。
- 根据首个 flags&4 分段、实际大小及 flags&0x80 构造固件范围；旧分支扣除 2 MiB。
- flags&0x10 控制 PB 大小/地址；清除相关开关时按参考代码清零。
- 计算系统内存窗口大小并按 4 KiB 向上对齐。
- 保留原函数不更新的字节，不把已有描述全部清零；输入失败时保持输出不变。

额外拒绝截断信息、超出段表边界以及大小/地址运算溢出。参考函数本身缺少这些检查，
不能以其在畸形输入上的整数回绕结果作为可发布的数据。

接口中的 platform_18、platform_9d8、platform_9e0 保留原偏移名称，避免在未核实
完整 ABI 时给字段误命名。S3000 初始化 `14002d73c` 从 `141106b08` 复制的后两者
默认值分别是 `0x8000000000` 和 0，验证程序直接读取原 PE 常量确认。

## 验证与对当前地址选择的复核

`scripts/verify-guest-windows.py` 执行 `140026390` 的原始指令，没有钩掉其地址计算。
65 个案例覆盖当前设备信息及三个相关标志位的全部组合，改变系统内存及平台输入，
并用随机原缓冲区验证未写字段的保留。每例逐字节比较全部 280 字节并检查末尾哨兵。
15 个非法输入案例确认拒绝且输出不变，C 包装器启用 UBSan、Wall/Wextra/Werror。

从当前设备信息独立推导得到：

| 用途 | BAR 内偏移 | 大小 | GPU 物理地址 |
| --- | --- | --- | --- |
| 私有普通内存 | 0xa00000 | 0x1800000 | 0x605800000 |
| 固件分段 | 0x3f000000 | 0x4000000 | 0x771fef000 |

这与当前上传的表/辅助资源所在私有池及固件分段一致，未发现分区起点选择错误。
Windows 的 64 MiB 固件分段与实际 8 MiB 固件分配是两个大小，不能互相替换。

完整结果在 `guest-windows-validation.json`，CPU 样例在
`build/firmware/guest-windows-example.bin`。样例的系统内存输入使用本机 Linux MemTotal；
这是已说明的模拟输入，不声称与 Windows DxgkCbGetDeviceInformation 的数值完全一致。
BAR2 起始描述由样例显式提供，其他未核实初值用零示例，不能将样例直接发布到设备。

## 尚未完成的部分

280 字节是本次恢复的区域跨度，不是已证明的 Host 拷贝长度。此实现只刷新已知字段，
并未补齐所有原始字段的初始化来源。持久物理缓冲区、完整初始化、上下文发布及撤销
生命周期仍未接入运行模块；当前源码新增的是供后续集成的真实构造函数。
没有发 BAR1+0xf0/+0x70，没有替换当前通信模块，也没有新增或清除固件队列命令。
仍无 MTT render 节点，不能把本次离线验证当作硬件加速成功。
