# BO 到 GPU 虚拟地址映射

2026-09-28。按“先不管恢复，继续适配”推进内存路径。本轮只加载后立即卸载了两份
纯 RAM 自测模块；未加载生产模块、未写设备，没有执行恢复或宿主操作。

## 实现

`kernel/mt_gpu_vm.h` 复用已通过 Windows 原始指令对照的三级 MMU 构造器，
将普通显存 BO 的 GPU PA 映射到指定 GPU VA。每次修改先在独立临时缓冲区重建页表，
检查成功并取得对象引用后才替换已提交镜像；失败保留原映射、引用和上传状态。
解除绑定要求 VA 和长度完全匹配，不隐式拆分范围。提交复制整个页表容量，清除
缩小映射后残留的条目。

每个绑定各持有一次 BO 引用，同一对象可以绑定多个不重叠的虚拟地址；关闭创建者
引用不会提前释放被 VM 引用的显存。拒绝跨设备/后端、虚拟地址重叠、页表自身、
物理范围与整个页表分配重叠、越界、非页对齐和不支持的标志。BO 容器由调用者拥有，
必须比所有 VM 引用活得更久；后续 GEM 层还需要保证容器本身的生命周期。

VM 销毁也先做全量引用预检：聚合每个 BO 的映射引用，并核对有效引用能否覆盖映射与
CPU/GPU pin；只有全部通过才逐项归还。发现失衡时返回 `-EUCLEAN`，保留 VM 和所有尚未
归还的引用，避免部分拆除。322 项 fence RAM 检查和280项 GEM RAM 检查通过，记录见
[VM 销毁回归](vm-teardown-atomicity.md)。

`kernel/mt_vm_vram.h` 提供内核后端：在普通显存池创建页表 BO，分配 CPU 镜像与
临时缓冲区，通过现有 I/O 拷贝接口上传并完整读回比较，只有一致才记录 uploaded。
所有操作由现有会话锁串行化。上传不发布根地址或敲 doorbell。

准备发布时调用 seal，要求非空且已完成上传校验；封存后拒绝绑定、解除绑定、再次
上传和销毁。当前没有实现在线 TLB 失效及上下文撤回协议，因此没有解封或强制释放
接口。seal 本身也不代表 GPU 已接受根页表。实际发布路径以后必须先封存再提交。

主模块外层设备对象加入地址空间管理器，buffers 属性新增 address_spaces 计数，
移除检查活跃地址空间。原 `struct mt_guest` ABI 保持不变。默认只初始化管理器，
尚无 ioctl 创建地址空间，不自动分配、上传或发布 VM。

## 验证

`tests/gpu_vm_test.c` 用实际 BO/VM 核心和 RAM 后端执行以下检查，页表由独立遍历器
解码，而非复用生产编码函数：

- 跨 1 GiB 边界的三个页面、40 位高位地址和 PTE 标志；
- 地址重叠、越界、错误后端、页表对象、引用溢出拒绝后旧状态不变；
- 页表容量耗尽时回滚，同一 BO 多地址映射的逐绑定引用；
- 所有者关闭后映射仍保有显存，解除映射后的旧条目和尾页清零；
- 上传前拒绝封存，封存后拒绝修改或销毁，最终分配释放平衡。

ASan、UBSan、Werror 通过；运行上下文、试验生命周期及 BO 回归通过。内核 W=1
构建通过，pahole 对照确认原共享结构不变。最新结果和模块 SHA256 见
[集成构建记录](runtime-integration-build.json)。

另重跑 `scripts/verify-mmu-bootstrap.py`：38 个稀疏树案例、129 个页表页面、
3 个默认映射案例与原始 Windows 指令一致，14 个错误输入拒绝案例通过。
该对照验证基础页表编码和构造；VM 引用和事务语义属于新增 Linux 适配实现，
不是对 Windows 完整 VM 管理器的等价证明。

复现命令（项目目录下）：

```sh
python3 scripts/verify-runtime-integration.py
python3 scripts/verify-mmu-bootstrap.py
```

## 当前限制

沿用 bootstrap 构造器上限：4 KiB 页、40 位地址、最多 16 个范围、64 个页表页、
累计映射 64 MiB。这是未发布地址空间的初步管理器，尚非通用可动态修改的 GPU VM。
GPU 任务使用引用、读写 fence、调度、GEM handles、用户态 mmap 和提交 ABI 尚未接入。
显存上传/读回后端本轮仅完成内核构建，没有实机执行；RAM 测试不验证 PCI 排序、
GPU 页表遍历、TLB 行为或硬件渲染。
